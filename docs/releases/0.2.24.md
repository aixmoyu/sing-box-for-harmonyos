# 0.2.24 更新说明

未签名测试发布；内核仍为 sing-box 1.14.4。本版处理 WebRTC IPv6 泄露。

## 截图结论：确实存在 IPv6 泄露

- IPv4 出口是 `192.255.193.139`（美国），和代理节点一致，IPv4 走的是代理。
- 但 `My IP` 和 Google / Cloudflare / NextCloud 的 STUN 结果里同时出现了 `240e:462:c1c0:…`，中国电信的公网 IPv6。
- 这个地址不属于代理节点，是手机自己在蜂窝网络下的 IPv6。也就是说 **IPv6 的 HTTP 与 STUN 流量没有进入 VPN 隧道**，直接从物理网络出去了；页面还标了“IPv6 优先”。

## 原因

1. 之前的测试都在只有 IPv4 的 Wi-Fi 下，检测页显示 “IPv4 Only”，所以这个泄露一直没有暴露；换成有 IPv6 的蜂窝网络后才出现。
2. 应用确实向系统声明了 IPv6：VPN 配置里有 IPv6 地址、`::/0` 默认路由和 `isIPv6Accepted: true`。但在该机型/系统上 IPv6 没有被真正收进隧道，浏览器仍然可以直接用蜂窝 IPv6。
3. 基础配置里带了 IPv6 地址，应用据此把 IPv6 判定为“开启”，DNS 因此会返回 AAAA，浏览器于是优先走 IPv6。

## 本版修复（保守、先止血）

- 基础配置改为 **IPv4-only**：TUN 只声明 `172.19.0.1/30`。
- 这会自动触发隐私层：在 TUN 内加入 IPv6 拒绝规则，并把 DNS 策略设为 `ipv4_only`，浏览器拿不到 AAAA，WebRTC / 普通请求不会再发起 IPv6 连接。
- 基础配置页增加说明文字，明确“按 IPv4 构建，IPv6 被拒绝”。
- 你自己导入的、配置里确实包含 IPv6 的配置仍按原规则“有 IPv6 就开启”，但同样存在系统未捕获的风险；在确认前建议优先用基础配置。

## 代价与后续

- 基础配置下无法访问纯 IPv6 站点（国内绝大多数站点有 IPv4，不受影响）。
- 要恢复 IPv6，需要真机确认系统是否真的安装了 `::/0`：手机连上无线调试后执行 `ip -6 route`，看默认路由是否指向 VPN 接口。确认能捕获后再把基础配置改回双栈，并加运行期校验。
